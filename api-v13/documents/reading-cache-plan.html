阅读段落：冷启动与缓存

范围：/v3/tipitaka-reading、Laravel library 阅读器、三藏下载打包（含 mobile 离线包）。两大块：A. 冷启动（没命中时一块只查几次库）与 B. 缓存（命中时不查库）。2026-11-22，方案稿，未动代码。

CBETA 那块 1384 ms 里数据库占 617 ms，其余约 770 ms 是 PHP 渲染与写缓存。另外两处这两个样本没触发、但模板多的 channel 会放大：

  • Markup 的取数是「一次 renderMany 一批」（术语 TermLoader、引用句子 SentenceLoader、channel 名 ChannelDirectory、QaLoader、TplLoader 都是 whereIn），但现在一段调用一次 renderMany，所以是每段一批：200 段带术语就是 200 次术语查询。
  • 批注正文逐条渲染：renderAnnotationNote() 每条批注单独调一次 MarkupService::render()，批注里有术语就每条各查一次。

A. 冷启动：按块渲染，一块只查几次库

A1 批量渲染  PaliContentService 新增 readParagraphs(int $book, array $paras, string $channel, string $format)，单段的 readParagraph() 改为调它（传一段）——只有一份渲染逻辑。没命中的那些段一起渲染：

  1. channel 查一次（现在每段一次）。
  2. 句子查一次：where book, channel, paragraph in (未命中的段) order by paragraph, word_start。
  3. 批注查一次：所有句子的 uid 一次 whereIn('res_id', …)，在 PHP 里按句分组；injectAnnotationNotes() 改为接收已取好的批注，不再自己查。
  4. 标题级别与 class 查 L0（见 B 部分），不落库。
  5. 一次 renderManyAs() 渲染全部句子：Resolver 收集整块的术语 / 引用 / 模板，各类只查一次。
  6. 批注正文也合并成一次 renderMany()（现在每条批注一次 render()）。

结果：200 段从约 2000 次查询降到约 4 次（channel、句子、批注、page() 的候选），外加每类模板数据各一次。CBETA 那块的 617 ms 库时间预计降到几十 ms；剩下的是渲染本身的 CPU，改完再量。

A2 谁受益

  • page()：一块里没命中的段交给 readParagraphs() 一次渲染（与 B 的批量读同一个入口）。
  • 阅读器：L3 章节缓存没命中时，整章的段一次交给 readParagraphs()。
  • 下载打包：经 page() 自动受益。cs6 整 channel html 打包 2286 s，大部分花在逐句批注与逐段查询上，这一步对它影响最大。

注意：批量取句子时要保持现有口径——strlen > 0、句子按 word_start 排、段内「有评估的句子之外补灰色对勾」的规则按段计算，不能变成按块计算。

B. 缓存

B 的方案：五块缓存，只给 readParagraph 改内部、不套外层

两个调用形状不同，缓存也分开：

  • 阅读器按章读：resolveDisplayRange() 算出整章区间，fetchRangeContent() 一次拼完，不切块。区间只由经文静态数据决定，同一章每次都一样 → 缓存整章成品，一次 GET。
  • /v3/tipitaka-reading 与下载打包按块读：块的边界取决于调用方的 page_size / unit / 游标，各不相同 → 缓存段落与索引，按块现拼。

L0 书目元数据  pali_texts 的静态列按书缓存：para → [level, class, lenght, chapter_len, chapter_strlen, toc]。

  • key：/pali-meta/{book}/v{N}，30 天；经文重新导入时把代码里的 N 加一（与 TipitakaCatalogService::CACHE_KEY 同一做法）。同一进程内再用数组记住。
  • 使用方：readParagraph() 未命中时取标题级别与 class；page() 的字节模式；阅读器的 resolveDisplayRange()（现在每次查本书全部章节行）；导出的 headingLevels()。

L1 段落成品  readParagraph() 直接缓存完整结果（含外壳 <div id='para-N'> / <hN> 与段后脚注列表）。

  • 外壳只依赖 L0 的 level / class（经文静态数据），放进缓存不会过时，所以不需要外层：把那两次查询挪进缓存闭包、改查 L0，签名与返回形状不变。
  • key：/read-para/v4/{book}-{para}/{channel}/{format}（换版本号，旧 key 自然过期）。没有译文的段也缓存（空 display）。
  • 失效：沿用 forgetParagraph()（句子、批注的模型事件已接好），改成删新 key。TTL 改用专门配置 mint.cache.read_paragraph_ttl（见「需要你定的」）。

版本号  每个 (channel, book) 一个递增计数 /read-gen/{channel}/{book}（RedisCache::increment，不过期）。

  • 句子、批注的模型事件里，在 forgetParagraph() 旁边加一次 increment：这本书的译文变了。
  • L2、L3 的 key 都带上它。版本一变，旧 key 不再被读到、自然过期，不用去找「哪些章包含这一段」再逐个删（父章、子章、下钻后的区间互相重叠，精确删除很难）。
  • 代价：一次多读一个小 key；编辑某本书时只有这本书的索引和章节缓存失效，别的书不受影响。

L2 内容索引  「某 channel 哪些段有译文」，给 page() 用：

  • /read-index/{channel}/books/g…：有译文的书号；/read-index/{channel}/{book}/g{gen}：该书有译文的段号（升序）。书号列表用 channel 级版本号（同样在句子事件里加一）。
  • page() 的候选段、游标、total / remaining 全在 PHP 里对这个数组算，命中时 0 查询；游标格式 {book}-{para} 与响应不变。
  • 重建只需一条 select distinct paragraph；cs6 最大的一本书一万多段，几十 KB；TTL 7 天。

L3 章节成品  给阅读器：整章拼好的 HTML 一次存、一次取。

  • key：/read-chapter/{channel}/{book}-{start}-{end}/g{gen}，值 {display, title}。start / end 由 resolveDisplayRange() 算（查 L0，不落库）。
  • 命中：读版本号 1 次 + 读章节 1 次，正文部分 0 查询。未命中才逐段 readParagraph()（各段多半已在 L1）拼好回写。
  • 只动 BookController::fetchRangeContent() 这一个方法：先查 L3，没有再走原来的拼接。
  • ?comm= 注释注入（injectNoteMarkers）在取出后做，不进缓存，不影响命中。

L4 批量读  只给 page()：一块最多 200 段，逐段 GET 是 200 次往返。

  • RedisCache 加 many()（phpredis 的 RedisCluster::mget，按 slot 拆到各节点）；readParagraph 加批量版 readParagraphs()：先 many() 拿命中的，没命中的逐段渲染回写。
  • 已在开发集群验证：200 个 key 落在 200 个 slot，mget 全部取对。本机往返近乎为零，看不出差别；收益与生产上 PHP 到 Redis 的往返延迟成正比（1 ms 往返时一块省约 200 ms）。
  • 阅读器不需要它：整章已有 L3。可以放到最后做，或先测生产延迟再决定。

风险与需要你定的

待定 1：L1、L3 的 TTL。段落与章节成品除了句子与批注（有精确失效），还依赖没有失效信号的数据：术语释义（{{term}}）、引用的其他句子（{{sent}}、义注对应）、channel 名称等。它们改了，缓存会旧到过期为止。

  • A（推荐）：24 小时。现在默认是 10 小时，旧内容最多多留半天；命中率大幅提高。
  • B：7 天，另加一个全局「渲染代号」，术语保存时加一，所有段落与章节按需重渲。术语编辑很频繁时会反复整库失效。
  • C：维持现状（跟 mint.cache.expire）。

待定 2：L4 做不做。阅读器不需要；只对 page() 有用，收益取决于生产上 PHP 到 Redis 的往返延迟。可以先上 L0–L3，量一下生产延迟再定。

  • 绕过模型事件的写入：全仓库只找到 InitCommentary 一处对 sentences 批量 delete()；以后新增批量写入要手动加版本号，在 ParagraphIndexService 类注释里写明。
  • Redis 占用：L1 key 数与现在相同，只是活得更久；L3 每个被打开过的 (channel, 章) 一个 key，正文几十 KB；版本号每个 (channel, book) 一个小 key、不过期；L0 共 217 个。
  • v4：v2 不读这些缓存，不受影响。

分步实施

  1. L0 书目元数据（A、B 都要用）。
  2. A1 批量渲染 readParagraphs()：冷启动从约 2000 次降到约 4 次；同时它就是 B 的批量入口。
  3. L1 段落成品（含外壳）：命中时 page() 403 → 3，阅读器正文 51 → 0。
  4. 版本号 + L3 章节成品：阅读器整章一次 GET。
  5. L2 内容索引：page() 命中 3 → 0。
  6. （视生产延迟）L4 批量读。

每步单独可测、可回退。
